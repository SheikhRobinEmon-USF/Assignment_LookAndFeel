Who it's for

Theme parks were my assigned topic, and it turned out to be a good one. USF sits right next to Busch Gardens Tampa Bay, and Orlando's parks are about an hour and a half up I-4. I approached the site the way I'd approach any product: start with a real user and a real problem.

The audience is young families. That means parents planning a Florida trip with kids of roughly 3 to 12, and the kids themselves, who mostly want to know which coasters they are finally tall enough for. Height minimums are spread across dozens of park pages, and finding out at the front of a long line that a child is two inches short ruins the day. So the home page opens with a height checker that shows every ride a rider can board, park by park.

The look and feel

I wanted the site to feel like a sunny day at the park: cheerful enough for a seven year old and still clear enough for a busy parent. The pages sit under a sky blue backdrop with drifting clouds and a string of pennant bunting below the menu. Cards look like bold outlined stickers in sunshine yellow, cotton candy pink, mint and sky blue, and the striped ruler with its pink star comes straight from the height signs at ride entrances. In dark mode the sky turns into a starry night at the park.

Headings use Fredoka, a rounded and friendly typeface. Body text uses Atkinson Hyperlegible, which the Braille Institute designed to be easy to read, because parents should never have to squint at a height requirement.

Animation adds to the fun without getting in the way. A little coaster car rides the track across the home page, balloons bob beside the height sign and the numbers count up as the page loads. When a child grows past a height line, the newly unlocked rides pop, and confetti falls once every ride is open to them. Cards bounce in and charts grow into place as you scroll. Anyone who turns on reduced motion in their device settings gets a calm, still version of the site.

Built for every screen

Parents look things up on their phones while standing in line, so the site had to work just as well on a small screen as on a laptop.

  • Layouts reflow from 320 pixel phones to wide desktop monitors, and text and spacing scale smoothly in between instead of jumping at a few fixed sizes.
  • On phones the ride table turns into easy to scan cards, and the menu folds into a single button.
  • Buttons, icons and the height slider are at least 44 pixels tall so small fingers can tap them, and the slider has an extra large handle.
  • Charts redraw to fit their space whenever the screen size or orientation changes.
  • The site keeps clear of phone notches and home bars, and follows the device's light or dark setting.

How I built it

I started with the data, because a data site is only as good as its numbers. Attendance comes from the TEA/AECOM Global Experience Index, the standard industry report. I checked every ride's minimum height, speed and opening year against the parks and public ride references. That check caught real changes: Hollywood Rip Ride Rockit closed in August 2025, and Big Thunder Mountain reopened in 2026 with a lower 38 inch minimum. Closed rides are not on the list.

Next I planned four pages around one consistent menu, then built a small design system first: colors, type scale, spacing, shadows and animations defined once in a single stylesheet, so every page shares the same look.

A few decisions shaped the build:

  • No CSS framework, no third party fonts. Bootstrap was allowed, but hand written CSS kept the stylesheet small and let the site look like its subject instead of a template. The fonts are trimmed to the characters the site uses and hosted in the repository, so pages make no extra requests to other servers.
  • D3.js from the CDN. The charts use D3.js v7.9.0 from the jsDelivr CDN, and it loads only on the analytics page. A copy of the same release lives in the repository as a backup, so the charts still work if the CDN is ever blocked.
  • One shared data store. The Manage rides page mocks create, read, update and delete operations on a ride list saved in the browser tab. The height checker and the analytics charts read the same list, so a ride added on one page shows up on the others.
  • Lightweight animation. Every animation uses CSS or a few lines of JavaScript, with no animation library, and none of them blocks the page from loading.
  • Accessible by default. Every page has a skip link, visible keyboard focus and labeled form fields. Forms explain exactly what to fix, every color pair passes contrast checks, and every chart has a data table view and colors tested for color blindness.

What I learned

The biggest lesson was that a data site is only as trustworthy as its data. I assumed ride details would be easy to look up, but checking each one turned up a ride that had closed in 2025 and another whose height minimum had changed. If I had copied numbers from memory or a single list, the site would have looked polished and still been wrong.

I also learned how much of good design is invisible. Getting the CRUD form to feel right took more work than building it: clear error messages, putting the cursor back where the user started after a dialog closes, and an undo button so a delete isn't scary. Running an accessibility check showed that some of my gray text was too light to read comfortably, which I never would have noticed by eye.

Designing for families taught me that a playful look has to earn its place. Bright colors, rounded type and a coaster car are fun, but they only work if a parent can still find an answer in a few seconds on a phone. Small wording choices mattered too: "5 more rides open up at 48 inches" turns a rule into something a child can look forward to. Keeping the fun and the clarity together meant checking every color for contrast and making sure the animations switch off for anyone who prefers less motion.

Finally, coming from product management, I enjoyed making the tradeoffs myself instead of writing them in a spec. Skipping Bootstrap, trimming the fonts and loading the chart library only where it is needed were small choices, but together they kept every page fast on a phone. Next time I would sketch the mobile layout first, since most of my layout fixes came from testing on small screens.

Technology

Technologies used to build Coaster Coast
HTML5Semantic page structure, native dialog elements for the ride forms, accessible tables and form controls.
CSS3One stylesheet with custom properties, fluid type, grid and flexbox layouts, keyframe animations, a dark theme and responsive table layouts for phones.
JavaScriptPlain JavaScript with no build step. Handles the height checker, the mock CRUD with validation and undo, the mobile menu, scroll animations and the coaster that rides across the home page.
D3.js v7.9.0Loaded from the jsDelivr CDN with an integrity check. Draws the bar, line and step charts with tooltips, direct labels and responsive resizing.
Web storagesessionStorage keeps ride edits for the current browser tab, so the CRUD page behaves like a real database without a server.
FontsFredoka for headings and Atkinson Hyperlegible for body text, self-hosted as WOFF2 files under the SIL Open Font License.
GitHub PagesHosts the site straight from the repository.
